### 2026-07-06 — Frontend-first verification with localStorage

**Context:** The project has no backend yet (all mock data + localStorage). We need to build the shop verification system.

**Decision:** Build the entire verification wizard and state management on the frontend using React Context + localStorage, matching the existing pattern used by `seller.tsx`, `cart.tsx`, `partner.tsx`, and `tracking.tsx`.

**Alternatives considered:**
1. Wait for backend — would block all verification UI work.
2. Build a minimal backend first — too much scope for this sprint.

**Consequence:** When the real backend (Supabase/Postgres) is connected, the localStorage state will need to be replaced with API calls. The types and UI components should remain the same. The `verification.ts` types are designed to match the planned database schema exactly, so the migration should be straightforward.

### 2026-07-06 — Gating selling features via VerificationLockGate

**Context:** Non-verified shops should not be able to list products or accept orders.

**Decision:** Created a `<VerificationLockGate>` component. If the shop's verification status is not `approved`, this component blocks layout rendering and displays a lock overlay with progress stats and a CTA button pointing to onboarding.
We wrapped the main views in `seller.orders.tsx` and `seller.products.tsx` with this gate, disabled the "Open Shop" settings switch in `seller.settings.tsx` for non-verified shops, and added an effect hook in `SellerProvider` (`seller.tsx`) that automatically forces `shop.isOpen` to `false` if verification status is not `approved`.

**Alternatives considered:**
1. Global router-level redirect: Too disruptive since the seller still needs to access settings, verification history, and the dashboard index.
2. Silent disabling of buttons: Confusing UX; rendering an explicit lock overlay clearly explains *why* the page is locked.

**Consequence:** Gating is strictly enforced on the frontend. The dashboard index (`/seller`) remains accessible so sellers can see the `VerificationStatusCard` and click "Verify Shop".

### 2026-07-07 — Mobile App Strategy: React Native & Expo (TypeScript)

**Context:** The project requires a cross-platform mobile client for Buyers and Drivers, with key requirements for background GPS location tracking, Supabase integration, and zero development budget (solo founder).

**Decision:** Build the mobile apps using **React Native with Expo** (using a monorepo structure to share database schemas, types, validation rules, and Supabase client logic with the Vite web client).

**Alternatives considered:**
1. Flutter (Dart): Offers slightly more consistent UI rendering and standard widgets, but requires learning Dart and leads to 0% code reuse, doubling maintenance effort.
2. Native Android/iOS (Kotlin/Swift): Best system integration, but requires two independent developers/codebases, which is too expensive for a solo founder.

**Consequence:** NearCart's entire codebase remains in a single language ecosystem (TypeScript) and single framework context (React). We can share types, schemas (Zod), and GPS location helpers directly via a shared library.

### 2026-07-09 — Server-side document verification pipeline, superseding pure-localStorage analysis

**Context:** The 2026-07-06 decision put the whole verification flow (including document "analysis") on the frontend with localStorage. That's fine for wizard progress/UI state, but document authenticity/duplicate checks can't be trusted if they run client-side — a seller's browser could just fake a pass.

**Decision:** Added `src/lib/verification/backend.server.ts` (server-only, `.server.ts` suffix keeps it out of the client bundle) with a real pipeline: SHA-256 duplicate detection across all merchants, AI vision OCR + quality + authenticity checks via the Lovable AI gateway, comparison against the registration form, a weighted confidence score, and a VERIFIED/UNDER_REVIEW/REJECTED decision. Files go to a private Supabase Storage bucket (`merchant-verification`); every action is written to an append-only `events` table for audit.

**Alternatives considered:**
1. Keep analysis client-side, only move final storage server-side — doesn't solve the trust problem (fraud detection is the whole point of Phase 1's fraud-flag rules engine).
2. Dedicated `shop_photos`/`fraud_flags` tables as originally documented in `plan/03-database-schema.md` (Phase 2) — the shipped pipeline uses a generic `events` table instead; not yet reconciled with the schema doc.

**Consequence:** Wizard *progress* state (which step you're on, form field values) still lives in localStorage per the 2026-07-06 decision — only document analysis moved server-side.

**Update 2026-07-10 — confirmed, not just suspected:** `StepDocumentUpload.tsx` does not call the new pipeline at all; it still simulates an upload with `setTimeout` and a synthetic filename. A repo-wide search found zero callers of `submitVerificationFile` / `getVerificationSubmission` / `finalizeVerification` / `getVerificationFileUrl` outside `api.functions.ts` itself. The backend is built and functional but entirely disconnected from the UI — treat Phase 8 as "backend done, integration not started," not "done." Also confirmed: `plan/03-database-schema.md` §3.1 still documents dedicated `shop_photos`/`fraud_flags` tables that the shipped pipeline doesn't use (it writes to a generic `events` table instead) — the schema doc is now out of sync with the implementation and needs a decision on which one is authoritative.

**Update 2026-07-10 — wiring fixed:** `StepDocumentUpload.tsx` and `StepShopPhotos.tsx` now use a real file input (`fileToBase64()` helper added to `verification.ts`) and call `submitVerificationFile`. Per-item status is driven by the real `FileAnalysis.decision` (`VERIFIED`/`UNDER_REVIEW`/`REJECTED`) rather than assumed. `l2_documents.status` and `l5_gps.status` in `VerificationWizard.tsx` now derive from actual per-item statuses (rejected/verified/submitted) instead of being force-set to `"verified"` on any upload. Final submit calls `finalizeVerification` and maps its real decision to `overallStatus`/`flagged`/`flagReasons`, with a loading state on the submit button. Note: `LOVABLE_API_KEY` is not set in `.env`, so `visionAnalyze()` in `backend.server.ts` will hit its catch-all fallback (quality 0.4, authenticity 0.5, empty OCR) for every file until that key is added — in practice this means most/all documents will land in `UNDER_REVIEW` rather than auto-`VERIFIED`, which is a safe failure mode but worth fixing before relying on the pipeline's AI checks. The schema-doc mismatch (`shop_photos`/`fraud_flags` vs. the generic `events` table) is unchanged and still needs a decision.

### 2026-07-10 — Guest browse + auth-at-checkout for customers; immediate auth for shop owners/partners

**Context:** User asked how the app should start and how account creation should work for all three user types (customer, shop owner, delivery partner), and specifically asked to check how Zomato and Blinkit do it. The existing `plan/04-user-journeys-screens.md` had the customer flow as mandatory login (Splash → Phone OTP → OTP verify → Profile setup) *before* the home screen — i.e. before showing any value.

**Research (web search, 2026-07-10):**
- Zomato: location permission is requested early with a soft "why" prompt before the native dialog; login supports phone/OTP, Google, Facebook, Apple ID. ([Zomato UX Breakdown — location flow](https://medium.com/@kvividsnaps/zomato-ux-breakdown-how-location-access-flow-is-designed-78cc8fbd1aea), [Onboarding teardown](https://medium.com/accredian/streamlining-the-user-journey-a-teardown-of-zomatos-onboarding-process-aa829aa582cc))
- Blinkit delivery-partner/picker onboarding (the workforce side) requires immediate phone+OTP, then Aadhaar OTP verification, before anything else — no browsing without an account. ([Blinkit Delivery Job guide](https://alphareach.tech/blog/blinkit-delivery-job-2026/), [Blinkit Picker Onboarding](https://play.google.com/store/apps/details?id=com.blinkit.storeob))
- Quick-commerce UX analyses note the design target is a search-to-checkout flow under ~45 seconds, and that the large majority of orders are reorders, not new discovery — reinforcing that friction before the first browse (not before checkout) is what kills conversion. ([Quick Commerce UX — ProductGrowth](https://productgrowth.in/insights/ecommerce/quick-commerce-ux/))
- Serviceability (is this location covered by a store's delivery radius) is checked from a raw lat/lng or pincode, independent of login, and gates whether the app can show anything useful at all. ([Pincode Serviceability Insights](https://www.actowizsolutions.com/pincode-serviceability-blinkit-zepto.php))

**Decision:**
1. **Customer app:** location/serviceability gate first (GPS with soft-ask, falling back to manual pincode/address search; a waitlist screen if unserviceable) → then full guest browsing (home, search, shop detail, cart) with **no login required** → phone+OTP is only asked for when the user taps Checkout, and a successful OTP verify doubles as silent account creation (first time) or login (returning), followed by merging the guest's client-side cart into the account.
2. **Shop owner and delivery partner apps:** login stays mandatory and immediate — there is no meaningful "guest" experience for a dashboard that's 100% the user's own business/work data. `/sell` → "Get started" and `/partner` should both hit an OTP gate before anything past the marketing page.

**Alternatives considered:**
1. Mandatory login before browsing for everyone (the previous plan-doc default) — rejected as friction with no offsetting value this early in the journey; not how any of the cited competitors do the consumer side today.
2. Guest access for shop owner/partner apps too (e.g. read-only preview dashboard) — rejected; these apps have no content to preview before an account exists (empty catalog, no assignments), so a login gate costs nothing.

**Consequence:** `plan/04-user-journeys-screens.md` §1a and §2 were rewritten to reflect this. The real blocker for building any of it is that `/auth/otp/*` doesn't exist yet (`backlog.md` → Auth System, entirely unbuilt), and `/seller`, `/sell`, `/partner`, `/admin/verification` currently have zero route guards — anyone can hit the seller-verification wizard with no account. The existing verification wizard (Phases 1–8) also has no "create shop" step in front of it; it assumes a shop already exists in `SellerContext`. Building the guest-cart-merge-on-login flow (customer side) and the route guards + shop-creation step (seller/partner side) both depend on the same underlying OTP/JWT auth service, so that's the actual next build order, not three separate flows.

### 2026-07-12 — Built the location gate + dev-mode OTP auth + route guards; deliberately deferred shop/partner creation

**Context:** Followed up on the 2026-07-10 decision by actually building the pages: the customer location gate, a shared phone+OTP auth system, the checkout auth gate, and route guards for `/seller` and `/partner`.

**Blocker found mid-build:** `SUPABASE_SERVICE_ROLE_KEY` in `.env` is invalid — direct-tested against the live project (`admin.from("events").select()`) and it returns `Invalid API key`, while the anon key works fine against the same project. This means the already-shipped verification pipeline's Supabase writes (storage upload, audit trail, duplicate detection) have been silently failing. This is a blocker for building anything that needs real server-side persistence, including proper OTP/session storage — the user needs to replace it from Supabase Dashboard → Project Settings → API; it can't be regenerated from code.

**Decision:** Given the broken service-role key, and that `otp_codes`/`users`/`user_roles` tables from `plan/03-database-schema.md` don't exist in the live project yet either, built the OTP/session system entirely client-side for now (`src/lib/auth.tsx`): generates a real 6-digit code, verifies it for real (not "accept any code" like the existing seller-wizard mock), but shows the code via a dev-mode toast instead of an SMS (no provider configured). Session and a phone→user registry are persisted to localStorage — the registry simulates the `users` table so the same phone number maps to the same account across visits. This mirrors the exact reasoning of the 2026-07-06 "Frontend-first verification with localStorage" decision: ship something fully testable now, swap the storage layer later without changing the UI.

Scoped down what actually got built vs. deferred, rather than rushing a bigger refactor:
- **Built:** location/serviceability gate (`src/lib/location.tsx`, `src/components/LocationGate.tsx`) wired into `AppShell`; shared auth (`src/lib/auth.tsx`, `src/components/PhoneOtpAuth.tsx`); checkout gated behind login (`checkout.tsx`); `/seller/*` and `/partner/*` layouts gated behind login (`seller.tsx`, `partner.tsx`).
- **Deliberately not built:** a real "create my shop" / "register as a partner" step. `SellerProvider` and `PartnerProvider` both hardcode a single fixed demo profile (`ramesh-stores` shop, one rider) for every session regardless of who's logged in — swapping that for real per-account data is a bigger refactor of how those contexts seed data, and doing it hastily risked breaking the order dashboard, products page, and partner assignment flows that depend on that seed data today. Flagged clearly in `backlog.md` instead of quietly leaving it half-done.
- **Deliberately not gated:** `/admin/verification`. Gating it with plain phone+OTP would be actively misleading — it would let any customer who logs in reach the admin queue, since there's no `user_roles`-based authorization behind it yet. Leaving it open (with the gap documented) is more honest than a fake-looking security gate.

**Alternatives considered:**
1. Wait to build anything until the service-role key is fixed and `otp_codes`/`users` tables are migrated — would block all forward progress on something the user explicitly asked to build now.
2. Build the full shop/partner-creation refactor in the same pass — rejected as too large and risky to bundle with the auth-gate work; better as its own reviewed change.

**Consequence:** Every customer route today requires setting a serviceable location before anything renders (persisted in localStorage, so returning visitors skip it). Checkout, `/seller/*`, and `/partner/*` all require phone+OTP login (dev-mode code shown via toast). Logging in as a "seller" still lands you on the same hardcoded `ramesh-stores` demo shop regardless of phone number — that's the next concrete piece of work, not a bug in what shipped today.

### 2026-07-12 (follow-up) — Real per-account shop creation and partner registration

**Context:** Immediate follow-up to the same session's location-gate/auth work. `SellerProvider` and `PartnerProvider` both handed every logged-in account the same single hardcoded demo profile (`ramesh-stores` shop; "Arjun Kumar" rider), which meant logging in as two different phone numbers just showed you the same fake data twice — not a real per-account experience.

**Decision:** Re-keyed both contexts' localStorage persistence by auth user id (`nearcart-seller-shop-${userId}`, `nearcart-partner-profile-${userId}`, etc.) instead of one fixed global key. Added `hasShop()`/`createShop()` (seller) and `hasProfile()`/`createProfile()` (partner) helpers, plus real creation-form components (`CreateShopStep.tsx`, `CreatePartnerProfile.tsx`) shown by the route layout when an account has no shop/profile yet. New accounts start genuinely empty — zero products/orders/jobs — rather than inheriting the rich demo seed data, matching what a real new signup would see.

**Alternatives considered:**
1. Keep the single global demo shop as a "shared showcase" and bolt per-account data on top — rejected, it's confusing to have two different data models coexisting and doesn't match how the app will actually work with a real backend.
2. Pre-seed a few starter products/orders for new accounts so the dashboard isn't empty on first login — rejected as unnecessary polish; empty-by-default is the honest, correct behavior and the seller dashboard already has "add product" flows to fill it in.

**Found but deliberately not fixed in this pass:** `verification.ts`'s `VERIFICATION_STORAGE_KEY` is still one global key, not per-shop — see the new item logged in `backlog.md` under Auth System. Fixing it properly also requires updating `admin.verification.tsx` (which reads that same fixed key in three places), which is a wider change than this pass was scoped for.

**Consequence:** Two different phone numbers logging in as sellers (or partners) now get fully independent data. The existing demo seed data (`ramesh-stores`, the seeded orders/jobs) is no longer reachable through the normal login flow — it only mattered for the old single-tenant demo mode, which this change intentionally supersedes.

### 2026-07-12 (follow-up 2) — Verification storage keyed per-shop; admin queue now scans all real shops

**Context:** Immediate follow-up closing the gap flagged in the previous entry: `verification.ts` still used one global `VERIFICATION_STORAGE_KEY` for every shop's verification progress, and `admin.verification.tsx` read/wrote that same fixed key directly in three places. With shop creation now real and per-account (previous decision), two different sellers doing verification at the same time would have silently overwritten each other's progress in that one shared key.

**Decision:** Replaced the constant with `verificationStorageKey(shopId)` (`nearcart-verification-${shopId}`), keeping `loadVerification`/`saveVerification`'s existing signatures and merge/backfill logic unchanged — only the underlying key changed. Added `listAllVerifications()`, which scans `localStorage` for every key matching that prefix, for the one place that genuinely needs to see *all* shops at once: the admin queue. `admin.verification.tsx` now merges every real shop's `pending_review` verification into its queue alongside the existing hardcoded `MOCK_PENDING_SHOPS` demo entries, and `handleApprove`/`handleReject` go through `loadVerification`/`saveVerification` scoped to the selected shop instead of blindly reading/writing one shared key (guarded so mock-only demo shops, which were never persisted, are left alone rather than creating orphan localStorage entries).

**Alternatives considered:**
1. Leave it as a known limitation since it only matters when testing two seller accounts concurrently — rejected since the fix was small, self-contained, and directly extends the shop-creation work from the same session.

**Consequence:** `admin.verification.tsx`'s queue is now a real (if still localStorage-only) reflection of every shop that has actually submitted for review, not just whichever one shop last saved. Verified live (headless render of `/admin/verification` still shows the queue with no crash) and with a clean full-project `tsc --noEmit`.

### 2026-07-12 (follow-up 3) — Admin route gated with a phone-number allowlist

**Context:** The 2026-07-12 decision above deliberately left `/admin/verification` open, reasoning that gating it with plain phone+OTP would be misleading — any customer could log in and reach the admin queue, since there was no role concept behind it. That's still true in the abstract, but leaving a real admin surface completely open is worse than a simple, honest stopgap.

**Decision:** Added `src/lib/admin.ts` — an `isAdminPhone(phone)` check against `VITE_ADMIN_PHONES`, a comma-separated allowlist read from `.env` (same `import.meta.env` access pattern already used in `supabase.ts`). `admin.verification.tsx` now requires login (phone+OTP, same as everywhere else) and then checks the phone against the allowlist; a non-admin logged-in account sees a clear "Not authorized" screen instead of the queue. This is a real authorization check (not "anyone who logs in gets in"), just backed by an env-configured list instead of a database role.

**Alternatives considered:**
1. Leave it open, as originally decided — rejected on reflection; an honestly-labeled temporary gate is strictly better than no gate at all, as long as it isn't dressed up as more secure than it is.
2. Build the full `user_roles` table now to do this "properly" — rejected as out of scope for this pass; that requires the Supabase service-role key to actually be valid (still broken) and real migrations, which is separate work already tracked in `backlog.md`.

**Consequence:** `isAdminPhone()` is intentionally the *only* place that encodes "how do we know someone's an admin" — swapping it for a real `user_roles` lookup later means changing one function, not every call site. Verified live (`/admin/verification` shows the login gate for a fresh session) and with a clean full-project `tsc --noEmit`.

### 2026-07-12 (correction) — SUPABASE_SERVICE_ROLE_KEY was never actually invalid

**Context:** Earlier in this session (see the 2026-07-10/07-12 entries above), I tested the service-role key directly against the live Supabase project and it came back `Invalid API key`, while the anon key worked fine. I reported this as a likely rotated/revoked key needing regeneration from the Supabase dashboard.

**What actually happened:** While adding `VITE_ADMIN_PHONES` to `.env` at the user's request, reading the file directly (rather than through my earlier line-splitting parser) showed the real problem: line 7 had `SUPABASE_SERVICE_ROLE_KEY="...signature"` and `SUPABASE_URL="https://..."` concatenated on the same line with **no newline between them**. Any parser reading that line captured the entire rest of the line — including the literal text `SUPABASE_URL="https://ibsrorhppcnzjrwfcdyb.supabase.co"` — as part of the service-role key's value. That corrupted string is what Supabase was correctly rejecting as an invalid key. The key itself was fine the whole time.

**Fix:** Split the two variables onto separate lines in `.env`. Re-tested the service-role client directly against the live project immediately after — it now successfully queries the `events` table (confirmed, not assumed).

**Consequence:** The verification pipeline's Supabase-dependent writes (`backend.server.ts` — storage upload, audit trail via `events`, duplicate detection) were likely working correctly all along in terms of code, but silently failing at the credential layer due to this file corruption, not a real backend/pipeline bug. Worth actually testing a document upload end-to-end now to confirm the fix holds in the running app, not just in this direct Node test. This also unblocks moving OTP/session storage off localStorage onto real Supabase persistence, since the previous blocker (thought to be a dead credential) is resolved.

### 2026-07-12 (planning) — Backend API structure: TanStack Start server functions + Supabase Auth

**Context:** User asked to plan the real backend APIs and data, and pick the best API structure. `plan/02-api-contracts.md` already documented a full REST-style contract (`/api/v1/...`, `Authorization: Bearer <jwt>`) written before any real backend existed. The only backend actually shipped (`src/lib/verification/`) doesn't look like that at all — it's TanStack Start server functions (`createServerFn`) called directly from the client, with a `.server.ts` file holding the real logic. Also noticed: `plan/03-database-schema.md` §5's RLS policies already write `auth.uid() = user_id` — that only ever resolves to a real value when Supabase Auth (not a custom JWT service) issued the session, meaning the schema was implicitly designed assuming Supabase Auth all along.

**Decision:**
1. **Transport:** every internal operation (auth profile, catalog, orders, seller ops, partner ops, admin) is a TanStack Start server function, organized one domain per folder under `src/lib/server/<domain>/{backend.server.ts, api.functions.ts}` — the exact two-file split verification already proved out. The only real HTTP endpoint anywhere in the plan is the payment gateway webhook (`src/routes/api/payments/webhook.ts`), because that's called by a third party, not our own client.
2. **Auth:** Supabase Auth's native phone OTP (`signInWithOtp`/`verifyOtp`), not a hand-rolled JWT/OTP service (user confirmed, recommended option). `public.users` becomes a profile table whose `id` **is** `auth.users.id` (not a separate generated UUID), populated by an upsert-on-first-login server function. `otp_codes` is dropped from the schema — Supabase owns OTP state.
3. Kept `plan/02-api-contracts.md`'s existing endpoint list as the authoritative *capability* contract (field names, request/response shapes, role requirements) — added a new §0 explaining how each maps to the real implementation, rather than rewriting 300+ lines of already-correct content.
4. Logged the phased build order in `backlog.md` (Phase A–H): schema migrations first, then catalog, then orders, then seller/partner ops, then payments, then admin, then realtime — each phase swaps one domain's localStorage mock for real Supabase-backed calls without changing the existing React Context/hook shapes, so it ships incrementally.

**Alternatives considered:**
1. Traditional REST API on a separate Node/Express service — rejected; adds a whole second deployable and duplicate type definitions for no benefit in a framework (TanStack Start) built around colocated server functions.
2. Custom JWT/OTP service as originally scoped — rejected (see auth decision above); more custom security code with no upside now that Supabase Auth is confirmed working and the RLS design already assumes it.
3. GraphQL — never seriously on the table; the data-fetching patterns here (nearby shops, order detail, dashboards) are naturally suited to typed RPC calls, not a generic query language.

**Consequence:** Nobody needs to invent request/response shapes — `plan/02-api-contracts.md` already has them; the work is wiring server functions in `src/lib/server/**` that match it, migrating the schema via Supabase migrations, and swapping each domain's localStorage persistence for those calls, one backlog phase at a time.

### 2026-07-12 (Phase A) — Initial schema migration written, not yet applied

**Context:** Started Phase A of the backend build-out (schema migrations). Checked for a way to apply DDL directly: no Supabase CLI installed, no `pg` package, and `.env` only has the REST-API service-role key (now working, per the earlier correction) — not a direct Postgres connection string/password. PostgREST (what `supabase-js` talks to) doesn't support arbitrary DDL execution, only CRUD on existing tables/views.

**Decision:** Wrote `supabase/migrations/0001_initial_schema.sql` — the full schema from `plan/03-database-schema.md` translated to real SQL, with the two 2026-07-12 decisions applied (`otp_codes` dropped; `users.id references auth.users(id)`), plus the `on_auth_user_created` trigger and `has_role()` helper, plus GRANTs/RLS policies for every table per §5's rules. Left the existing `events` table completely untouched (already in use by the verification pipeline; don't know its exact current schema/RLS and didn't want to risk disturbing working infrastructure). Since there's no way to execute it from here, the plan is: hand the file to the user to run once via Supabase Dashboard → SQL Editor, then verify programmatically afterward (same direct-Supabase-query technique used to catch the service-role key issue) that the expected tables now exist.

**Alternatives considered:**
1. Install the `pg` package and ask for the raw database password to run it programmatically — rejected; that's a new dependency plus a new sensitive credential flowing through chat/tool calls for what's a one-time action. Pasting into the SQL Editor needs nothing new from the user.
2. Install and interactively log into the Supabase CLI — rejected; `supabase login` requires an interactive browser flow this environment can't complete non-interactively, and `supabase db push` still needs the DB password.

**Consequence:** `supabase/migrations/0001_initial_schema.sql` exists in the repo as a reviewable, version-controlled artifact per the schema doc's "Migration discipline" (§7), but is **not yet live** — Phase A isn't done until the user runs it and it's verified. Table/type creation is written idempotently (`if not exists` / duplicate-object-safe `do` blocks) so re-running it is safe; the RLS policies are not (re-running after a successful apply will error on duplicate policy names, which is an acceptable signal that it already applied).

**Update 2026-07-12 — applied, one real bug found and fixed:** User ran `0001_initial_schema.sql`. Verified all 25 new tables exist (direct query, service-role client) — confirmed. Verified RLS: public tables (`categories`/`shops`/`products`/`reviews`/`shop_hours`) correctly readable by the anon key. But `orders` and `payments` failed with **"infinite recursion detected in policy for relation orders"** — `orders_partner_read` queried `assignments` (a normal table reference, triggering assignments' own RLS), and `assignments_shop_read` queried `orders` right back, forming a cycle. This would have blocked real customers/shop owners/partners from reading their own orders and payments, not just anon — a functional bug, not just a security non-issue.

**Fix:** `0002_fix_orders_assignments_rls_recursion.sql` — added `is_order_partner()`/`is_order_shop_owner()`, both `security definer` (the same mechanism `has_role()` already relies on: the function runs with its owner's privileges, which owns the tables, so its internal query bypasses RLS instead of re-triggering the other table's policies), and repointed `orders_partner_read`/`assignments_shop_read` at them. User ran it; re-verified — the recursion error is gone, `orders`/`payments` now return empty results cleanly instead of erroring.

**Known limitation, not yet resolved:** `users`/`user_roles`/`wallet_ledger`/`kyc_documents` all show "anon query succeeds, 0 rows" — that's the *expected* shape of correct RLS behavior (silent row-filtering, not a thrown error, since `auth.uid()` is null for anon so every `= auth.uid()` condition is false), but it's not provably safe yet since these tables are empty — there's no real row to confirm anon can't see it. Also reconfirmed `tsc --noEmit`/`eslint` clean.

**Consequence:** The startup warning should no longer fire (confirmed at the code level — `createCsrfMiddleware` attaches the exact `csrfSymbol` the check looks for; did not have direct access to tail the background dev server's stdout to visually confirm, but the mechanism and the functional 403/pass-through behavior are conclusive). ### 2026-07-22 — Fixed the partner-side double-accept race found by the QA sweep

**Context:** User asked to fix the remaining item from the sweep — two different delivery partners, each holding their own "offered" `assignments` row for the same order, could both call `acceptJob` and both succeed (no guard existed at all).
